# Artifact & Storage Lifecycle Specification

**Capability** C6 — Artifact & Storage Lifecycle · **Lane** SHR · **Change** `audio-extract-vertical-slice`

## Purpose

The storage port and the lifecycle of the bytes: three zones with server-generated keys, an atomic
promote as the only route to a canonical artifact key, scratch that is always cleaned up, and an
artifact record that is a pointer plus metadata. Per ADR-0001, the port is a semantic contract; the
local filesystem adapter ships now and an S3 adapter must be installable later without touching the
domain model.

**In this slice:** the port contract, the three zones and their key shapes, worker read-only on the
inbox zone, streamed writes, atomic promote, scratch deletion on every exit path, the artifact
record, and a declared 7-day retention policy with `expires_at` written.

**Not in this slice:** any retention sweep or janitor, orphan-artifact sweeping, and URL ingestion
into the inbox zone. Because no sweep ships, an expired artifact record may still exist; the job
remains `succeeded`, and the response case is specified by the download grant capability.

## Requirements

### Requirement: One Storage Port With Semantic Verbs and No Filesystem Leak

All storage access MUST go through a port exposing exactly the semantic operations `putScratch`,
`promote`, `createReadGrant`, and `remove`. The port contract MUST NOT expose filesystem verbs such
as `rename`, `read`, or `delete` by path, and MUST NOT expose raw URLs, bucket names, or paths in
its types. The local filesystem adapter and a future S3 adapter MUST be interchangeable behind the
port, selected by configuration, without changing the domain model.

#### Scenario: The port contains no filesystem vocabulary

- GIVEN the storage port interface
- WHEN it is inspected
- THEN it exposes only the semantic operations
- AND no operation takes or returns a filesystem path or a raw storage URL

#### Scenario: A second adapter needs no domain change

- GIVEN a second storage adapter implementing the port
- WHEN it is configured instead of the local adapter
- THEN the job pipeline code is unchanged
- AND no domain type names a storage backend

### Requirement: Storage Keys Are Server-Generated

Every storage key MUST be generated by the server from job and attempt identities. The client's
filename MUST NOT be used as, or as part of, a storage key, and no storage key segment may come
from client input. Path traversal and key collision through client data MUST therefore be
impossible by construction.

#### Scenario: A hostile filename never becomes a key

- GIVEN an upload whose display filename contains directory separators
- WHEN the input is stored
- THEN the storage key is the server-generated key for that job and ordinal
- AND the filename appears only as display metadata

#### Scenario: Keys are derived, not accepted

- GIVEN any storage operation initiated by a client request
- WHEN the key is computed
- THEN the key is derived from server-side identities
- AND no client-supplied string is used as a key segment

### Requirement: The Three Zones Have One Writer Each

The system MUST use exactly three storage zones with these key shapes: the inbox zone
`inbox/{job_id}/{ordinal}` written only by the API, the work zone `work/{job_id}/{attempt_no}/`
written only by the worker executing that attempt, and the artifact zone
`artifacts/{job_id}/{artifact_id}` written only through promote. The worker MUST be read-only on the
inbox zone. A non-terminal job's input MUST NOT be deleted.

#### Scenario: Each zone has a single writer

- GIVEN the running system
- WHEN storage writes are inspected per zone
- THEN the inbox zone is written only by the API
- AND the work zone is written only by the worker for that attempt
- AND the artifact zone is written only through promote

#### Scenario: The worker cannot write to the inbox

- GIVEN a job whose input is in the inbox zone
- WHEN the worker writes to the inbox zone
- THEN the write fails

#### Scenario: A pending retry keeps its input

- GIVEN a job that is still non-terminal
- WHEN storage retention logic is considered
- THEN its inputs are not deleted

### Requirement: Bytes Are Streamed Through the Port

The port MUST accept a byte stream for writes and MUST NOT require the caller to buffer a whole
object in memory. A storage adapter MUST NOT load an entire input or artifact into application
memory to satisfy a write.

#### Scenario: A large input is stored as a stream

- GIVEN an input at the job-type size cap
- WHEN it is written through the port
- THEN the bytes are written incrementally to disk
- AND memory use does not grow in proportion to the object size

### Requirement: Promote Is the Only Route to a Canonical Key, and It Is Atomic

`promote(ref)` MUST make a complete set of bytes appear at the canonical artifact key atomically,
or fail leaving nothing at that key. No partial or in-progress bytes may ever be readable at a
canonical key. The local adapter MUST obtain atomicity from a rename on the same volume; an S3
adapter MUST obtain it from complete-object PUT semantics. Re-promoting to an existing canonical key
MUST overwrite it atomically rather than producing a partially visible object.

#### Scenario: A reader never sees partial bytes

- GIVEN a promote that has not yet completed
- WHEN a reader requests the canonical key
- THEN the reader either sees the previous complete object or nothing
- AND never a truncated or partial object

#### Scenario: A failed promote leaves no artifact

- GIVEN a promote that fails partway
- WHEN the canonical key is inspected
- THEN nothing is readable there
- AND no artifact record is created by that promote

#### Scenario: Re-promoting to the same key overwrites

- GIVEN a canonical key that already holds a complete object for that job
- WHEN promote is called again for the same key
- THEN the key holds exactly one complete object
- AND no reader observes a mixture of the two

### Requirement: The Canonical Key Is Never Written Directly

No component other than the promote operation MAY write to the artifact zone. Handlers MUST NOT
resolve or write a canonical key, and the API MUST NOT write artifact bytes.

#### Scenario: Direct writes to the artifact zone are rejected

- GIVEN a write attempt to a canonical artifact key that did not come from promote
- WHEN the write is issued
- THEN it is rejected
- AND the artifact zone is unchanged

### Requirement: Scratch Is Deleted on Every Exit Path

The worker MUST delete its attempt's scratch prefix on every exit path — success, failure, and
timeout. Because the deletion is by prefix, partially written outputs must not survive. No scratch
content may be reused across attempts; each attempt writes under its own `work/{job_id}/{attempt_no}/`.

#### Scenario: A successful attempt leaves no scratch

- GIVEN an attempt whose outputs were promoted
- WHEN the attempt ends
- THEN its scratch prefix is gone

#### Scenario: A failed attempt leaves no scratch

- GIVEN an attempt that failed partway and wrote partial outputs
- WHEN the attempt ends
- THEN its scratch prefix is gone
- AND the partial outputs are not readable

#### Scenario: Attempts do not share scratch

- GIVEN two attempts of the same job
- WHEN each writes its outputs
- THEN each writes under its own attempt-scoped prefix
- AND one attempt cannot read the other's partial files

### Requirement: An Artifact Record Is a Pointer Plus Metadata, Never Bytes

The database MUST store an artifact record containing an `artifact_id`, the canonical
`storage_key`, `byte_size`, `content_type`, a `checksum`, the display `filename`, `created_at`, and
`expires_at`. The database MUST NOT store artifact bytes. The canonical key MUST be the only bridge
from the record to the bytes, and the display filename MUST NOT grant any access on its own.

#### Scenario: Bytes live outside the database

- GIVEN a completed job with an artifact
- WHEN the artifact record is read
- THEN it contains the canonical storage key and metadata
- AND no byte content is stored in the database

#### Scenario: The record points at promoted bytes

- GIVEN an artifact record
- WHEN its canonical key is resolved through the storage port
- THEN the complete promoted object is found
- AND a recreate of the record is not required to find it

### Requirement: The Output Size Cap Is Verified After Promote

The job-type registry MUST declare an output size cap per job type. After a successful promote and
before the outcome is committed, the worker MUST compare the promoted artifact's `byte_size`
against that cap. An artifact that exceeds the cap MUST fail the job with an error code and MUST
NOT be committed as `succeeded`, so an oversized output is never presented as a successful result.
Because the bytes were already promoted, they remain at the canonical key unreferenced by any job
row — the orphan case the design already accounts for; the deferred orphan sweep removes them.

#### Scenario: An oversized artifact fails the job

- GIVEN a job whose handler produced an artifact larger than the type's declared output cap
- WHEN the promoted artifact's size is checked
- THEN the job fails with an error code
- AND it is not committed as `succeeded`

#### Scenario: An artifact within the cap succeeds

- GIVEN a job whose artifact size is within the type's declared output cap
- WHEN the size is checked
- THEN no failure is raised for size
- AND the job may commit `succeeded`

#### Scenario: The cap comes from the registry, not from the handler

- GIVEN a job type with a declared output cap
- WHEN the check is performed
- THEN the cap value is read from the job-type registry
- AND the handler does not supply or override it

### Requirement: Retention Is Declared as Seven Days and `expires_at` Is Written

The system MUST declare a 7-day retention policy for inputs and artifacts, and MUST write
`expires_at` on every artifact record when it is created. This slice MUST NOT ship a retention
sweep: no process deletes expired artifacts or expired inputs, and no orphan sweep runs. Because
terminal states are immutable, a job whose artifact has expired MUST remain `succeeded`.

#### Scenario: `expires_at` is written at creation

- GIVEN a newly created artifact record
- WHEN it is read
- THEN `expires_at` is set 7 days after `created_at`

#### Scenario: No sweep runs in this slice

- GIVEN an artifact whose `expires_at` is in the past
- WHEN the system runs
- THEN no process deletes it or its input
- AND its artifact record is still present

#### Scenario: An expired artifact does not change job state

- GIVEN a `succeeded` job whose artifact has passed `expires_at`
- WHEN the job is read
- THEN its state remains `succeeded`
- AND no expiry state or state change is produced
